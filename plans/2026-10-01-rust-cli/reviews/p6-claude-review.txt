1. [med] A repo's .env can set the new RIVAL_HOME and move all of rival's session and queue state — crates/rival/src/root.rs:382
   main_entry runs `paths::load_dotenv()`, which loads `./.env` from the current directory (the reviewed repo). It then rebuilds the final config with `initial.reload_env(Paths::from_env())`. `Paths::from_env` (paths.rs:38-56) reads `RIVAL_HOME` first and treats it as the rival root. RIVAL_HOME is new in the Rust port (paths.rs:5 calls it a port addition), and it is normally unset in the user's environment. godotenv only refuses to override variables that are already set, so a `RIVAL_HOME=` line in a repo's .env always wins. In Go the root came from os.UserHomeDir/$HOME, which is always set in a shell, so a repo .env could not move it. The sessions dir, queue dir, queue lock and `.update-check` cache then all point wherever the repo chose. This contradicts the port's own rule that a reviewed repo's .env must not reconfigure rival: subprocess.rs blocks OPENCODE_/GROK_/KIMI_/etc. for exactly that reason. config.yaml is unaffected because it is read before .env.
   Scenario: A user runs a skill (`rival command codex --detach`) in a repo whose .env has `RIVAL_HOME=./.rival-dev`, or a deliberately crafted path. The session JSON (full review prompt and diff), the log and the queue ticket are written under the repo. The ticket sits in a separate queue dir with its own lock, so this run ignores the global RIVAL_MAX_CONCURRENT limit that other reviews obey. `rival tui` and Rival.app opened elsewhere never show the run. The repo-local .rival-dev can also end up committed with the prompt contents inside.
   Fix: Read RIVAL_HOME from the process environment captured before `load_dotenv` (as is already done for config.yaml and the wait default), or add RIVAL_HOME to the variables the .env loader refuses to set. Add a test showing that a cwd .env with RIVAL_HOME leaves `cfg.paths()` unchanged.
